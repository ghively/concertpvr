# v0.3 Audit Execution Plan

> **Companion to `2026-04-26-v0.3-audit.md`.** That doc diagnosed the gaps; this one closes them.
>
> **Goal:** ship `v0.3.0-rc1` in **one focused work session (≈6-8h)** with zero live-recording regressions and a complete bug catalog before we tag the final `v0.3.0`.

**Branch model:** all work lives on a new `phase-9.5-audit` branch off `main` at `b8e728c`. We tag `v0.3.0-rc1` from there, run real-world testing against rc1, and only then merge → tag final `v0.3.0`.

---

## Cross-cutting guardrails (apply to EVERY task)

1. **Live recording path is sacred.** Zero edits to `recorder.py`, `pool.py`, `buffer.py`, `recording_starter.py`. Any change that touches existing live tests must keep them green.
2. **Test count monotonically increases.** Never decrease. If a test fails post-fix, find out why before disabling.
3. **mypy + ruff stay strict.** No relaxations.
4. **Additive-only behavior.** New code paths gated on new state (`kind=video`, `watch_vod_uploads=true`, etc.). If a code path can be reached by a v0.2 user, it must produce v0.2-identical output.
5. **Failing test first, then fix.** Every bug from Stage 2 becomes a regression test in Stage 3 BEFORE the fix lands.
6. **Audit-at-every-step.** Each Stage commits → runs the harness → moves on. We don't batch fixes.
7. **Commit format:** `git -c gpg.format=openpgp -c commit.gpgsign=false commit -m "..."` always.
8. **Docker smoke after every fix wave.** A bad commit that breaks the build gets caught within minutes.

## Stage 1 — Build the audit harness (parallel, ~45 min)

Four independent harnesses. Different files, zero overlap, fully parallelizable. Three subagents + one inline.

### Stage 1 acceptance criteria

- [ ] All 4 harnesses exist as files in the repo
- [ ] Each harness can be invoked with a single command
- [ ] Each harness has clear pass/fail output (exit code + line count of failures)
- [ ] None of the harnesses run automatically in `pytest -q` (they're opt-in)
- [ ] mypy still clean, all 263 existing tests still pass

### S1.A — Frontend contract test scaffold (subagent, sonnet)

**File:** `tests/test_frontend_contracts.py` (new)

Hardcoded JSON literals copied from each frontend component's POST/PATCH body. Each test asserts the corresponding backend Pydantic schema accepts it without 422.

Coverage scope:
- `SmartPasteModal` channel-result panel → `ChannelWatcherCreate`
- `SmartPasteModal` playlist-confirm panel → `PlaylistConfirmRequest`
- `WatcherDetail` Settings tab → `ChannelWatcherPatch` (all 9 new VOD fields)
- `Settings` page → `SettingsPatch` (incl. `max_concurrent_vod_downloads`, `auto_delete_source_after_publish`)
- `PostDownloadReview` → `SegmentCreate` (with new `genres` field)
- `BacklogBrowser` → `BacklogDownloadRequest`

Each contract is verified by:
```python
def test_smart_paste_channel_subscribe_payload_accepted():
    payload = {
        "channel_url": "https://www.youtube.com/@nprmusic",
        "watch_live": False,
        "watch_vod_uploads": True,
        "auto_publish": False,
    }
    parsed = ChannelWatcherCreate.model_validate(payload)
    assert parsed.watch_vod_uploads is True
```

Marker: `@pytest.mark.contracts` so we can run `pytest -m contracts` standalone.

**Acceptance:** `pytest tests/test_frontend_contracts.py -v` runs and reports any rejections clearly. Initial expectation: at least the playlist confirm + segments paths will surface schema mismatches we don't yet know about.

### S1.B — Real-yt-dlp integration test scaffold (inline, ~10 min)

**File:** `tests/integration/test_real_yt_dlp.py` (new)

Gated on `CPVR_INTEGRATION_TESTS=1`. Skip otherwise. Tests:
- Probe `https://www.youtube.com/watch?v=dQw4w9WgXcQ` → assert all `StreamInfo` fields populate.
- Probe a known channel → assert `probe_channel` returns sensible data.
- `list_recent_uploads` against `@nprmusic` → assert at least 5 entries with non-empty `youtube_id`.
- `expand_playlist` against a small known playlist → assert non-empty entries.

NOT included in `pytest -q` because they hit the network and take ~30s each.

**Acceptance:** running `CPVR_INTEGRATION_TESTS=1 pytest tests/integration/ -v` either passes or gives a clear diagnostic per failure.

### S1.C — Docker build smoke (inline, ~5 min)

**File:** `scripts/smoke-docker.sh` (new) + entry in `docs/release-checklist.md`

Script does:
1. `docker compose -f docker-compose.dev.yml build` — must exit 0
2. `docker compose -f docker-compose.dev.yml up -d` — must start
3. `curl -sf http://127.0.0.1:8787/api/healthz` — must return `{"status":"ok"}` within 60s
4. `docker logs concertpvr-dev | grep -i "ERROR" | wc -l` — must be 0
5. `docker compose -f docker-compose.dev.yml down`
6. Exit 0 if all above passed; exit 1 otherwise.

**Acceptance:** `bash scripts/smoke-docker.sh` runs to completion and exits 0 on a clean state.

### S1.D — End-to-end VOD flow harness (subagent, sonnet)

**File:** `scripts/smoke-e2e.sh` (new)

Container-based smoke that walks the actual VOD pipeline:
1. Start fresh container (delete `.local-data/metadata.db`, restart compose).
2. POST `/api/streams` with `https://www.youtube.com/watch?v=dQw4w9WgXcQ` → expect 201 + Stream JSON + `recording_id` returned.
3. Poll `/api/recordings/{id}` until `status="complete"` (cap 5 min).
4. Assert file exists at `.local-data/staging/vod-dQw4w9WgXcQ.mkv` (or whatever the path resolves to) with size > 1 MB.
5. POST `/api/segments` with `{recording_id, artist:"Rick Astley", start_s:0, end_s:30, genres:"Pop", source:"manual"}` → expect 201.
6. POST `/api/segments/{id}/publish` → expect 200.
7. Poll segment status until `status="published"` (cap 60s).
8. Assert directory exists in `.local-publish/` with `movie.mkv`, `movie.nfo`, `poster.jpg`, `fanart.jpg`.
9. Assert NFO contains `<genre>Pop</genre>` and `<title>Rick Astley`.
10. Cleanup (or leave artifacts for manual inspection).

**Acceptance:** `bash scripts/smoke-e2e.sh` exits 0 OR exits 1 with a clear "FAILED AT STEP N: <reason>" line.

## Stage 3 — Fix bugs (parallel where safe, ~2-4h)

Each finding from Stage 2 becomes one task. Tasks are batched into waves where files don't overlap, run in parallel within a wave.

### Stage 3 acceptance criteria

- [ ] Every finding from Stage 2 has a corresponding regression test (test added FIRST, watch it fail, then fix)
- [ ] After each wave: full unit-test suite passes (`pytest -q`), mypy clean, ruff clean
- [ ] After each wave: re-run the relevant audit harness; the previously-failing tests now pass
- [ ] Live recording tests stay green (assert `pytest tests/test_streams_api.py tests/test_recorder.py tests/test_pool.py -v` all pass after every wave)

### Wave 3.A — Contract fixes (high parallelism, low risk)

These are pure schema mismatches. Each task touches 1 file at most. Fully parallel via subagents (or inline if simple).

- 3.A.1: each contract failure from S2.1 → schema update + regression test
- Examples likely to be found:
  - `ChannelWatcherCreate` missed a field the frontend sends
  - `PlaylistConfirmRequest` missing optional fields with `extra="forbid"`
  - `SegmentPatch` doesn't accept `genres` despite the schema work in T1
  - `SettingsPatch` missing some new VOD field

**Per-task pattern:**
1. Add the failing contract test (already in S1.A — should now be red).
2. Update the schema.
3. Run contract tests → green.
4. Run full unit suite → green.
5. Commit with message `fix(schema): <field>` — one commit per file changed.

### Wave 3.B — Real yt-dlp / Docker integration fixes (sequential, medium risk)

These bugs likely require iteration with real outputs. Run sequentially because:
- Each fix may cascade into the next (e.g., output path issue blocks ffprobe step).
- Easier to root-cause one at a time.

For each finding from S2.2 + S2.3 + S2.4:
1. Reproduce in isolation via the harness.
2. Add the failing test (real-yt-dlp test or unit test depending on layer).
3. Fix the underlying issue.
4. Re-run the harness → green.
5. Re-run all unit tests → green.
6. Commit.

Specific suspected fixes from the audit doc:
- `vod_downloader` output path template — `%(ext)s` may need handling
- `Splitter.probe()` API mismatch — may need to be `Splitter.probe_media()` or `ffmpeg.probe()`
- Progress regex may not match yt-dlp's actual stdout format
- `list_recent_uploads` real-channel response may have unexpected entry shapes

### Wave 3.C — Frontend fixes (parallel within file boundaries, ~1h)

Run a manual frontend walk-through (`docs/operations/frontend-smoke.md` from S1 — written but unrun). For each broken interaction:
1. Identify the file (usually 1-2 components per bug).
2. Add an inline frontend behavior test if Vitest is available, OR add a backend contract test that catches the API-side cause.
3. Fix.
4. Rebuild + reload + re-test.

Specific suspected fixes:
- `SmartPasteModal` channel mode error UI on 409 (rather than raw "API error: 409", show "Already subscribed to this channel.").
- `PostDownloadReview` route param parsing — may not be wired to `useParams()`.
- `BacklogBrowser` "Queue N downloads" mutation — verify it actually fires.
- WebSocket VOD progress topic mismatch between backend (`recordings.{id}.progress`) and frontend listener.

### Wave 3.D — Migration safety (sequential, low risk)

If a real v0.2 DB snapshot exists:
1. Copy `metadata.db` from a v0.2-running deployment to `.local-data/v0.2-snapshot.db`.
2. Run `alembic upgrade head` against it.
3. Verify all rows post-migration are sensible (every existing watcher has `watch_live=true` and all new VOD-toggle defaults applied).
4. Commit a small new test file `tests/test_migration_0008_realistic_data.py` that constructs a realistic v0.2-shape DB then upgrades it.

If no v0.2 snapshot:
1. Synthesize one via test fixture: create the DB, INSERT rows matching v0.2 schema (no VOD columns, varying `title_filter`, multiple watchers, etc.), then upgrade.
2. Same verification.

### Stage 3 commit cadence

One commit per fix (so we can bisect later). Commit message format:
```
fix(<area>): <one-line summary>

Failing test: tests/<file>::<test_name>
Root cause: <one sentence>
Audit harness: <which harness caught it>
```

After each Wave (A, B, C, D) completes, run a "Wave completion check":
```bash
./.venv/Scripts/python.exe -m pytest -q
./.venv/Scripts/python.exe -m mypy src/
./.venv/Scripts/python.exe -m ruff check src/ tests/
bash scripts/smoke-docker.sh
```

All four must pass before moving to the next Wave. If anything fails post-Wave, fix before continuing.

## Parallelism strategy

We've now learned that:
1. Subagent worktrees on Windows have permission friction → prefer main worktree where files don't conflict
2. Some subagents go off the rails → keep prompts narrow, single-responsibility
3. Real-fail integration tests are slow → run during audit and release, not in `pytest -q`

So the parallelism plan:

| Stage | Concurrency | Reason |
|---|---|---|
| 1 (build harness) | 4 parallel (3 sonnet subagents + 1 inline) | Fully disjoint files |
| 2 (run audit) | sequential | Each harness independent but we want clear logs |
| 3.A (contract fixes) | up to 4 parallel | Each fix touches 1 schema definition; commits are tiny |
| 3.B (yt-dlp / Docker) | sequential | Bugs may cascade; iteration on real outputs |
| 3.C (frontend) | sequential within feature, parallel across features | Frontend pages are independent; same-page edits sequence |
| 3.D (migration) | sequential | Single test file |
| 4 (verify + tag) | sequential | One-shot |

Effective wall-clock: maybe 4-6h with focused execution, vs the 8h total estimate. Buffer in there for surprise bugs.

## Blast-radius commitments

Repeated from the cross-cutting guardrails for emphasis. **At every stage:**

- Live recording (`recorder.py`, `pool.py`, `buffer.py`, `recording_starter.py`) — UNTOUCHED.
- Existing live tests (`tests/test_streams_api.py` minus new VOD tests, `tests/test_pool.py`, `tests/test_recorder.py`, `tests/test_buffer.py`) — STAY GREEN.
- v0.2 DB users — migration adds columns only; existing queries unchanged.
- v0.2 API consumers — no endpoint removed, no required field added that wasn't already required.

If at any point one of these constraints is violated, STOP and revisit. We don't trade live-recording reliability for VOD features.

## What we explicitly do NOT do in this audit

- We do NOT add Vitest / Jest / Playwright to the frontend. Manual walk-through + backend contract tests cover ~95% of regressions.
- We do NOT redesign any v0.3 feature. The audit is about **verifying what we built works**, not changing what it does.
- We do NOT improve test coverage for live recording. Live is already green and stable; new tests focus on v0.3 surface.
- We do NOT add CI. Local run via release-checklist is enough for now.
- We do NOT introduce new dependencies. Every new test uses what's already in `pyproject.toml`.
