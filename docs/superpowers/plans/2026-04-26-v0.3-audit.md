# v0.3 Audit & Stabilization Plan

> **Do not execute this plan until reviewed and approved.** This is a diagnosis + remediation design, not an action list. The point is to enumerate every endpoint, every contract, every known/suspected bug, and every test gap — then build the missing test layers so v0.3 is genuinely shippable.

**Status of v0.3 today:** code complete, 263 unit tests passing, 5 bugs hit in 30 minutes of real use. The unit-test count is high but coverage of integration boundaries is low. We can't ship until we close that gap.

---

## Part A — Why our tests didn't catch these bugs

We've now hit 5 distinct production bugs that all slipped through 263 passing tests:

| # | Bug | Root cause in test design |
|---|---|---|
| 1 | `yt-dlp` not on PATH on Windows native | Every yt-dlp test uses `FakeProcessRunner` or monkeypatches `YoutubeDL.__init__`. No test ever spawns a real subprocess. |
| 2 | Dockerfile copies `src/` after `pip install .` | No test ever runs `docker build`. The release-checklist mentions Docker but it's a manual smoke step, never automated. |
| 3 | `POST /api/streams` doesn't route channel/playlist URLs | All tests post single-video URLs. The smart-paste routing was specced and frontend-implemented but the backend half was lost between Tasks 14 and 15. No test asserts that posting a channel URL returns `{type:"channel"}`. |
| 4 | `ChannelWatcherCreate.model_config = ConfigDict(extra="forbid")` rejects `watch_live` / `watch_vod_uploads` / `auto_publish` | Backend tests construct payloads with old fields only. Frontend sends new fields. No test exercises the actual frontend payload shape. |
| 5 | (latent) `vod_downloader` invoked `yt-dlp` directly — would fail in any environment without that on PATH | Same as #1. Docker has yt-dlp on PATH so it would have masked this in production until somebody ran without Docker. |

**The common pattern:** every bug lives at an **integration boundary** that our test pyramid doesn't cross.

```
   ┌─────────────────────────────┐
   │   Unit tests (263)          │  ← good coverage, but mocked at every boundary
   ├─────────────────────────────┤
   │   API tests (TestClient)    │  ← good for happy-path, but use synthetic payloads
   ├─────────────────────────────┤
   │   Frontend↔backend contract │  ← MISSING: nothing verifies what the UI actually sends matches what the API actually accepts
   ├─────────────────────────────┤
   │   Real yt-dlp / ffmpeg      │  ← MISSING: zero tests spawn the real binaries
   ├─────────────────────────────┤
   │   Docker build              │  ← MISSING: no automated `docker build` step
   ├─────────────────────────────┤
   │   End-to-end smoke          │  ← MISSING: no scripted "paste URL → see file in Emby" run
   └─────────────────────────────┘
```

We need to add the bottom four layers, even if minimally. Without them, every deploy is a guess.

## Part C — Known + suspected bug catalog

### Confirmed bugs (already fixed but need regression tests)

1. **yt-dlp PATH (vod_downloader.py)** — fixed by `python -m yt_dlp`. *Test gap:* no test spawns real subprocess. *Regression test needed:* a Docker-only integration test that calls `vod_downloader.download` against a tiny real YouTube URL.

2. **Dockerfile build order** — fixed by reordering `COPY src/` before `RUN pip install .`. *Test gap:* no automated docker build. *Regression test needed:* CI step (or release-checklist automation) that runs `docker build .` and fails the suite if it errors.

3. **`POST /api/streams` channel/playlist routing** — fixed in `streams.py` with URL regex classification. *Test gap:* no test posts a non-video URL. *Regression tests needed:* (a) post `https://www.youtube.com/@<handle>` → expect 200 with `type:"channel"`; (b) post `?list=<id>` URL → expect 200 with `type:"playlist"`; (c) post `?list=<id>&v=<vid>` (a watch URL with playlist context) → expect single-video path (because `watch?v=` is in URL).

4. **`ChannelWatcherCreate extra="forbid"`** — fixed by adding optional fields. *Test gap:* tests use minimal payload, never the smart-paste payload. *Regression test needed:* a "frontend contract" test that posts exactly what the SmartPasteModal sends.

### Suspected bugs (untested code paths likely to break in real use)

5. **`vod_downloader` actual subprocess invocation** — even with the `python -m yt_dlp` fix, we've never run a real download end-to-end. Possible follow-on issues: progress regex doesn't match yt-dlp's actual output format; output_path placeholder template (`{youtube_id}.%(ext)s`) might not work; `-f bestvideo*+bestaudio/best` might produce a file with an unexpected extension that ffprobe later can't find.

6. **VOD ffprobe step in main.py lifespan handler** — uses `Splitter(runner=AsyncSubprocessRunner()).probe(output_path)`. Never run against a real downloaded file. Possible failure modes: `Splitter.probe` API mismatch (was it `probe_media` originally?); ffprobe not finding the file because of `%(ext)s` template expansion; width/height/fps/duration_s extraction crashes on certain encodings.

7. **`channel_poller._check_for_new_vod_uploads` against real channel** — uses `list_recent_uploads(channel_url)` which is a flat-extract. Never run against a real channel. Possible issues: yt-dlp returns entries with shapes we didn't anticipate; `BroadcastInfo` dataclass field defaults don't match all upload types; date parsing fails for some uploads.

8. **`backlog GET` against real channel** — same as above. The marking logic that joins against existing Streams + Recordings to compute `state` is complex and untested with concurrent state.

9. **`DELETE /api/recordings/{id}/source` with real files** — never run with an actual file on disk. Need to verify (a) Path.unlink for single-file VODs, (b) shutil.rmtree for buffer dirs, (c) Windows-vs-Linux file lock differences.

10. **NFO emission in publisher with v0.3 fields** — new `<plot>` and per-genre `<genre>` lines. Not validated against actual Emby ingest. Emby is permissive but if our XML escaping breaks (e.g., description with `<`) we'd get a parse error in Emby's logs that we'd never see.

11. **Lifespan startup sequence with v0.3 additions** — orphan_recovery → vod_recovery → eager session_secret → register_app → scheduler → vod_queue. We've shown each step works individually. We have **not** verified the actual order of these in the running container, or that VOD queue rehydration recovers correctly across a real container restart with `vod_downloading` rows.

12. **Frontend `PostDownloadReview.tsx`** — the agent shipped this but I never opened it in a browser. Possible issues: route param parsing, missing data states, "Apply setlist" button doesn't actually create segments, "Publish to Emby" button doesn't call the right endpoint.

13. **Frontend `BacklogBrowser.tsx`** — same situation. Multi-select state management, "Queue N downloads" button wiring, sticky bulk-bar behavior — all unverified.

14. **Frontend `SmartPasteModal.tsx`** — three result modes, but only the channel mode was just verified (and only after fixing two backend bugs). Single-video and playlist modes are untested in browser.

15. **WebSocket VOD progress events** — backend publishes to `recordings.{id}.progress`; frontend listens to that topic. Have we confirmed the topic name and event shape match between the two sides?

16. **Migration 0008 against real v0.2 production DB** — we tested it on a fresh empty DB. Never tested upgrading a v0.2 DB with real rows (channel_watchers with title_filter set, streams with kind=video already, etc.). The Synology deploy will run this against a non-empty DB.

17. **Frontend `Library.tsx` and `Sources.tsx` genre filter** — bundle 1 agent noted "stream objects don't expose tags yet (deferred)" — meaning the genre filter on Sources is wired to UI state but doesn't actually filter. Need to confirm (a) backend Stream serialization includes `youtube_tags`, (b) frontend reads it, (c) filter logic actually narrows the visible list.

## Part D — New testing layers we need

We're not asking for 100% coverage. We're asking for **integration boundary coverage** where the bugs actually live.

### Layer 1 — Frontend contract tests (highest ROI)

A small new test file (~200 lines) that does the equivalent of:

> "For each component that POSTs/PATCHes, capture the literal payload it sends, then assert the backend Pydantic schema accepts that payload without 422."

Approach: extract the payload-construction logic out of each frontend component into pure functions, then test those functions in TypeScript AND test the backend's Pydantic schema accepts the resulting JSON in Python.

Realistic scope for v0.3:
- `SmartPasteModal.ChannelResultPanel` → POST `/api/channel-watchers` payload
- `SmartPasteModal.PlaylistResultPanel` → POST `/api/playlists/ingest/confirm` payload
- `WatcherDetail` Settings tab → PATCH `/api/channel-watchers/{id}` payload
- `Settings` page → PATCH `/api/settings` payload (specifically the new VOD fields)
- `PostDownloadReview` → POST `/api/segments` payload (with genres)

Implementation: add a new `tests/test_frontend_contracts.py` that hardcodes example payload JSON literals (copied from the actual frontend code) and asserts each schema accepts them. **No frontend tooling required** — this is a Python test file.

### Layer 2 — Real-yt-dlp integration tests (gated)

A separate test file `tests/integration/test_real_yt_dlp.py` that runs only when `CPVR_INTEGRATION_TESTS=1` is set. Tests:
- Probe `https://www.youtube.com/watch?v=dQw4w9WgXcQ` (the canonical test video) and assert all StreamInfo fields populate.
- Download a tiny < 30-second public video and assert file appears on disk + ffprobe reads it.
- List recent uploads on `@nprmusic` and assert at least one entry has expected shape.
- Expand a known small playlist and assert items list has expected count.

Run these manually before each release. Not in the normal `pytest -q` because they hit the network and are slow.

### Layer 3 — Docker build verification

Add to release-checklist (and potentially a CI step):
1. `docker compose -f docker-compose.dev.yml build` must succeed.
2. `docker compose -f docker-compose.dev.yml up -d` must start cleanly and the healthcheck must turn green within 60s.
3. `docker compose logs concertpvr-dev` must not contain "ERROR" at startup.

This catches regressions like the `src/` ordering bug.

### Layer 4 — End-to-end smoke harness

A `scripts/smoke-test.sh` (or `.ps1`) that:
1. Starts the dev container fresh.
2. Posts a known YouTube video URL and asserts a Recording lands in `vod_downloading`.
3. Polls until status hits `complete` (or fails out at 5 min).
4. Asserts the file exists in `.local-data/staging/` with non-zero size.
5. Posts a segment for the recording.
6. Calls publish endpoint.
7. Asserts a folder appears in `.local-publish/` with `movie.mkv` + `movie.nfo` + `poster.jpg` + `fanart.jpg`.
8. Asserts the NFO contains `<genre>`, `<title>`, `<year>`.
9. Cleanup.

Run before tagging a release. Documented in release-checklist.

### Layer 5 — Manual frontend walk-through script

A `docs/operations/frontend-smoke.md` checklist mirroring what a real user does:
- [ ] Open Sources page, click "+ Add URL".
- [ ] Paste single video URL → modal shows preview → click Queue → toast appears → recording in Recordings.
- [ ] Paste channel URL → modal shows channel preview → toggle VOD → click Subscribe → navigates to watcher detail.
- [ ] Paste playlist URL → modal shows item list → check 2 items → click Queue.
- [ ] Watcher detail Backlog tab → multi-select → "Queue N downloads".
- [ ] Recording detail page → progress bar advances.
- [ ] After complete → click "Open review" → segments form populates → fill artist + genres → click Publish.
- [ ] Library page filters by genre.
- [ ] Dashboard split-stat shows correct fractions.

Each step gets a screenshot in the markdown, so future regressions are obvious.

## Part E — Execution plan (don't run yet)

Proposed sequence — **review and revise before any of this runs**:

### Wave A — Verify what's already broken vs what's secretly broken (audit-only, no code)

1. Add the empty-DB version of `tests/test_frontend_contracts.py` with hardcoded payloads from each component. Run it. **Expected: red.** This is how we discover schema mismatches we don't yet know about.
2. Manually exercise every frontend route per the smoke checklist. **Expected: more 422s, more 4xxs.** Document each.
3. Run the end-to-end smoke harness against a real YouTube URL. **Expected: failure somewhere — likely in the download → ffprobe → review screen handoff.** Document.

Output of Wave A: a complete list of *all* outstanding issues (the 17 above plus whatever new ones we find).

### Wave B — Fix the contract drift

For each broken contract from Wave A:
- Decide canonical schema (backend or frontend wins).
- Update the loser to match.
- Add the contract test as a regression guard.

### Wave C — Real yt-dlp + Docker verification

- Implement the real-yt-dlp integration test set.
- Run them. Fix what breaks.
- Add Docker build to release-checklist.
- Add smoke-test.sh and run it. Fix what breaks.

### Wave D — Frontend manual walk-through with fixes

- Run the frontend smoke checklist tab-by-tab.
- For each broken step, root-cause and fix.
- Add a regression test (contract or integration).

### Wave E — Migration safety on real-shape DB

- Take a real v0.2 DB snapshot (or simulate one with realistic rows).
- Run alembic upgrade head on it.
- Verify all rows post-migration are sensible.
- Add this as a recurring release-checklist step.

### Wave F — Tag and ship

Only after A-E are green:
- Re-run the full unit suite + integration suite + Docker smoke + frontend manual walk.
- Tag v0.3.0 (or v0.3.0-rc1 first if we want a beta cycle).
- Deploy to Synology.

## Cross-cutting design principles for the audit

1. **No new code without a failing test first.** Every fix in Wave B-D starts with the test that would have caught it.
2. **No mocking at integration boundaries we haven't proven yet.** Real yt-dlp tests don't mock yt-dlp. Frontend contract tests don't mock the schema.
3. **Verify with curl + browser, not just pytest.** The pytest suite is necessary but insufficient.
4. **Migration safety is non-negotiable.** Don't break v0.2 users when they upgrade.
5. **Don't ship the audit and forget.** The integration test layers we build here become the new minimum for every future phase.

## Estimated scope

- Wave A (audit): 1-2 hours of mostly diagnostic work
- Wave B (contract fixes): probably 4-8 distinct bugs, each ~10-30 min
- Wave C (real yt-dlp + Docker): ~1-2 hours of test infra + iteration on real failures
- Wave D (frontend walk): ~30-60 min of clicking + ~1-2 hours of fixes
- Wave E (migration): ~30 min if v0.2 DB exists, else just synthetic data
- Wave F (ship): 30 min

Total: **half a day to a day** of focused work, vs the current trajectory of "ship + hotfix loop forever."
